# Fase 5.2 — Plataforma Agêntica: Fundação viva + Garantia + Quick-wins (Design/Spec)
**Data:** 2026-07-22 · Antecede: Fase 5.1 (superfície MCP + 4 paredes, deployada). Visão-mãe: `docs/fase5.2_plataforma_agentica_visao_2026-07-22.md`.

## Objetivo (uma frase)
Subir o **cérebro orquestrador** (Hermes headless, OpenAI, sem GPU) plugado na superfície MCP da 5.1, **com a camada de garantia embutida desde o dia 1** (groundedness gate + observabilidade + HITL 3-tiers + auditoria + idempotência), entregando quick-wins on-demand nos 3 ângulos (executivo, operacional, financeiro/jurídico) — provando a plataforma com risco contido e **sem retalho**.

## Arquitetura (3 frases)
Orquestrador de topo (Hermes) roteia por intenção; os 8 consultores + leitores são **tools** que ele encadeia; opera como orquestrador-único-com-tools mas **multi-agente-ready**. Toda resposta passa por um **guardrail de groundedness** (todo número rastreável a uma linha do banco) antes de chegar ao usuário; toda ação por HITL calibrado (auto/aprova-e-lembra/gate+OTP). Se o Hermes cair, o chat degrada para o `consultor_hub` direto (aditivo, não SPOF).

## Tech Stack
Hermes v0.19.0 headless (API Server OpenAI-compat) · OpenAI via roteador espelhando `core/llm_cascade.py` (tiers nano/mini/gpt-5) · conector MCP (`tools_include()` da 5.1) · FastAPI backend (`main_production`) · PostgreSQL · Redis (ConectaEventBus, só leitura de estado nesta fase) · OpenTelemetry GenAI → Langfuse (self-host) · container Docker ao lado do backend.

## Global Constraints (inegociáveis — herdadas)
- **Dinheiro que SAI / ato legal-externo = SEMPRE gate humano + OTP.** Nunca aprendível, nunca auto. Money-out fica fora do conector MCP.
- **Operacional (escala/alocação) = READ-ONLY** para o agente (lê/reporta, não altera; divergência = relatório).
- **Nunca fabricar dado.** `exibido == banco` é gate automático; "aguardando dado" é resposta correta quando não há fato; KPI sem fórmula = "—", nunca inventar.
- **LGPD:** retrato cruzado de cliente só na origem `ceo`; least-privilege por agente.
- **Deploy:** backend blue-green + baked; Hermes = serviço separado; `.env` na raiz.
- **Degradação honesta > invenção.** Hermes indisponível → `consultor_hub` direto.

## Bloco 1 — O motor Hermes (headless, na nossa infra)
- Serviço `conecta-pro-hermes` no compose, ao lado do backend. Headless: só o **API Server** (OpenAI-compat) chamado pela rede interna. `mem_limit 2g`.
- **Semente baked** (`.hermes.md` constituição): os inegociáveis + quem é o Conecta PRO + as raias dos 8 consultores + "nunca fabricar dado". Re-injetada a cada sessão (não drifta).
- **Memória aprendida** em volume nomeado (sobrevive rebuild); nesta fase só working + factual read (a memória-que-aprende é 5.5).
- **Cérebro OpenAI, zero-retention**, chave única da raiz `.env`.
- **Fiação MCP:** `config.yaml` → `mcp_servers.conecta_pro` (url do conector, auth, `tools.include` = `tools_include()`).

## Bloco 2 — Orquestrador + consultores como tools (multi-agente-ready)
- **Opera como 1 orquestrador + tools** (regra anti-multi-agente-prematuro). Os 8 `consultor_*` + leitores por domínio são as tools que ele encadeia.
- **Contratos de saída estruturados:** cada tool/consultor devolve dado **com proveniência** (`source`, `query`, `as_of`) — não prosa livre. É o que alimenta o gate de groundedness.
- **Teto de iteração + budget por tarefa** (anti-loop de delegação).
- **Ponto de entrada:** o chat dos consultores existente + um entry "Executivo/Orquestrador" (o dono pergunta cross-domínio). A ponte no backend chama o Hermes; health-check + fallback pro `consultor_hub` direto.
- **Multi-agente-ready:** a arquitetura já separa leitores/executores/consultores por allowlist; fatiar em sub-agentes reais (5.4+) não exige retrabalho.

## Bloco 3 — A CAMADA DE GARANTIA (o que faz "grande player", embutida já)
1. **Groundedness gate (anti-alucinação):** antes de a resposta ir ao usuário, um verificador confere que todo número/afirmação factual tem `source` de uma tool e bate com o banco (`exibido==banco`). Afirmação sem proveniência é bloqueada/reformulada. "Aguardando dado" é a saída válida quando vazio.
2. **Observabilidade OTel-GenAI → Langfuse:** cada passo (LLM, tool, retrieval) vira um span; tokens input/output separados; custo por trace; trajetória auditável. Instrumentação uma vez (OTel), backend Langfuse self-host.
3. **HITL em 3 tiers:** 🟢 auto (read) · 🔵 aprova-e-lembra (write reversível interno) · 🔴 sempre-gate+OTP (dinheiro/legal). Nesta fase (read-heavy) o foco é 🟢, com o esqueleto de 🔵/🔴 pronto pra 5.4.
4. **Auditoria append-only:** todo ato do agente (tool, args, resultado, trace-id) em log imutável ligado ao span. Requisito, não luxo (folha/fiscal/PIX).
5. **Roteamento de modelo por complexidade + budget:** classificador barato escolhe tier (nano/mini/gpt-5); **dinheiro/legal → sempre gpt-5**; budget USD/tokens por tarefa (estoura → degrada/pede humano). Espelha `core/llm_cascade.py` (`route_ex`/`aroute_ex`).
6. **Confiabilidade:** retries backoff+jitter; fallback de provider; **idempotency key** já no esqueleto das ações (anti PIX-dobro); degradação graciosa.

## Bloco 4 — Os quick-wins do 5.2 (3 ângulos, read-heavy)
**Executivo (dono):** briefing matinal 1-card (caixa + postos descobertos + prazos + deals) · **"posso contratar 3 porteiros?"** (orquestra CFO caixa + COO demanda + CHRO custo-CCT + Fiscal tributo) · runway ao vivo (corrige o KPI cache velho) · margem por condomínio (receita − folha alocada − custos).
**Operacional (gerente/supervisor):** **"quem está no posto Villa Dei Fiori hoje?"** (exige fechar o plumbing `shifts`) · postos descobertos agora/próximas 12h · faltas por porteiro (ranking) · custo de diaristas vs orçado.
**Financeiro/Jurídico:** runway + aging (quem deve, há quanto) · simulação de holerite CCT · contratos/certidões vencendo · dúvida fiscal com dado real.

**Plumbing a fechar nesta fase (habilita os quick-wins):** ligar `shifts` (turno-a-turno, nome+horário) ao panorama/uma tool de leitura de escala do dia por posto (gap `consultor_coo_service.py:63-73`); expor custo de diaristas do mês ao CFO.

## Bloco 5 — Degradação graciosa (aditivo, não SPOF)
Hoje os consultores respondem via `consultor_hub` direto. A ponte tem health-check: Hermes vivo → orquestra; Hermes caiu → cai pro `consultor_hub` direto (chat continua respondendo). Prova obrigatória: matar o Hermes → chat responde.

## Fora de escopo (fases seguintes — para NÃO virar retalho, ficam nomeadas)

- **5.4:** ações propor→aprovar em escala (🟡/🔴 gated: cobrança, lote de pagamento, substituição, kit, proposta, eSocial) + José Luís promovido a agente cliente-facing (allowlist mínimo, anti-injeção).

## Testabilidade / oráculos
- **Groundedness:** para cada quick-win, teste que o número exibido == query no banco (o `veracity-sweep` como gate). "Aguardando dado" testado quando vazio.
- Verificar pela **rota da tela** (a superfície real), numa bancada isolada (green/throwaway), nunca in-process no container público (OOM).
- Degradação: matar o Hermes → chat responde via `consultor_hub`.
- Observabilidade: cada quick-win gera trace OTel com spans + custo.

## Riscos abertos (a decidir no plano)
- Backend de observabilidade: Langfuse self-host vs OTel-collector+outro — confirmar footprint.
- O groundedness gate: verificador determinístico (regras de proveniência) vs LLM-judge leve — provável híbrido.
- O plumbing do `shifts`: nova tool de leitura vs enriquecer o panorama COO existente.
- Onde o Hermes roda: container fixo vs serverless — fixo recomendado (listener de memória/sessão).

## Resumo de 1 linha
5.2 sobe o Hermes como orquestrador dos consultores-como-tools, **com groundedness + observabilidade + HITL + auditoria + roteamento de custo embutidos desde o início**, entregando quick-wins nos 3 ângulos com risco contido — a fundação de grande player sem retalho.
