# Fase 5.4 — Ações propor→aprovar em escala (Design/Spec)
**Data:** 2026-07-25 · Antecede: 5.2a + peça 3 (chat escopado) + 5.3 (proativo), todos deployados. Discovery: `.superpowers/sdd/discovery-5.4-acoes.md`.

## Objetivo (uma frase)
O agente passa a **PROPOR ações** (nunca executar): a proposta cai numa fila de aprovação humana no sino pela matriz RBAC; ao humano aprovar (+ OTP quando dinheiro/legal), o **fluxo de execução JÁ EXISTENTE** roda. A 5.4 adiciona só a camada "agente propõe → fila" — zero código de execução no agente.

## Decisões do dono (delegação total: "resultado final, você decide e executa" — 2026-07-25; ver [[feedback_executar_sem_perguntar]])
- **6 ações, em 3 ondas por risco:** A) cobrança + proposta + kit (leve, prova a primitiva); B) substituição de posto (propor→humano; operacional é READ-ONLY); C) lote de pagamento + eSocial (🔴, reusa OTP/gov provados).
- **Gate por natureza:** dinheiro-que-sai (lote) + eSocial = 🔴 sempre OTP/humano; cobrança (money-in) + envio de proposta = 🟡 aprova sem OTP; kit = 🔵 auto (reversível interno); substituição = propor→humano aprova.
- **Aprovador por domínio (RBAC):** dinheiro/eSocial → diretoria (jjesus/pjesus) + OTP; substituição/kit → gestor operacional ou diretoria; proposta/cobrança → comercial + diretoria.
- **José Luís → fase separada 5.4b** (cliente-facing, o mais exposto a injeção; allowlist formal + pré-filtro determinístico + gate no link de assinatura — foco próprio). NÃO nesta fase.
- **Pré-step obrigatório:** resolver o drift `gp_justifications` status `'pending'` (inglês, do upload de atestado `portal_docs_ouvidoria`) vs canônico `'pendente'` — padronizar em `'pendente'` (writer + linha viva) antes de escalar propostas.

## Global Constraints (INVIOLÁVEIS — a fase inteira gira em torno disto)
- **O LLM NUNCA executa.** Toda tool de ação só faz INSERT de proposta PENDENTE na tabela nativa do domínio. Zero chamada de execução no handler. A execução é sempre disparada por HUMANO no fluxo existente.
- **Dinheiro que SAI = SEMPRE gate OTP humano.** Reusa `InterPaymentService` (preparar→OTP email TTL 300s→aprovar FOR UPDATE→executar atômico+idempotência), INTACTO. Money-out FORA do conector MCP. Teto `CONECTA_LIMITE_DIARIO_PAGAMENTOS` (R$100k) respeitado na proposta.
- **eSocial / ato legal = 🔴 gate humano** (transmissão gov real S-22x0 só após aprovação humana).
- **Operacional READ-ONLY** para o agente: substituição é PROPOSTA, nunca alteração de escala.
- **3 papéis nunca no mesmo ator:** quem PROPÕE (agente/usuário) ≠ quem APROVA ≠ quem gera/valida OTP ≠ quem executa. O "aprovar" é inforjável (ver [[feedback_loop_gates_inforjaveis]]).
- **Idempotência** (anti-PIX-dobro): correlation/idempotency key em toda proposta; 2 propostas idênticas não duplicam pendente nem execução.
- **RBAC por domínio** governa quem vê a tool de ação e quem aprova (reusa `user_modules`/roles da peça 3).
- **Nunca fabricar.** **Auditoria append-only** de todo passo (propor→aprovar→executar), ligada ao `agent_audit`.
- Deploy blue-green baked; celery reciclado quando aplicável; bancada throwaway (nunca green/:8080); teste que escreve limpa por id no finally (0 remanescentes), NUNCA apaga real; sem pytest; git add só dos próprios; commits --no-verify + Co-Authored-By Opus 4.8; TZ Manaus; casts ::text.

## Arquitetura (mínima, sem retalho — da discovery)
Uma **primitiva "Proposta de Ação"** reusando o `ToolDef`/engine da peça 3: cada ação = ToolDef cujo handler `async(db,user,scope,**args)` valida escopo/RBAC + grava **status pendente na tabela NATIVA do domínio** (não uma tabela genérica: `inter_payments` 'preparado', `proposals` draft, cobranças, `gp_justifications`, `op_substituicao_propostas` [nova], eSocial pendente) + idempotency + `agent_audit` + entrega no sino (5.3) pro aprovador por RBAC. A APROVAÇÃO/EXECUÇÃO reusa os fluxos humanos existentes (payment OTP, proposal send, kit_orchestrator, esocial_tasks). O molde canônico do handler é `tools_ponto.justificar_ajuste_de_ponto` (5.3).

## Componentes
1. **Pré-step:** normalizar `gp_justifications` para `'pendente'` (fix `portal_docs_ouvidoria` writer + a linha viva) + guard.
2. **Primitiva de proposta** (`orquestrador/acoes/base.py`): helper `propor(db, *, dominio, tabela, payload, gate, roles_aprovador, idempotency_key, user, scope)` → INSERT pendente + audit + entrega sino; fail-closed (sem roles_aprovador não registra). Gate declarado por ação (🔴/🟡/🔵).
3. **Onda A** (tools, execução já existe): `propor_cobranca` (🟡, `CobrancaService` alvo; money-in), `propor_proposta_comercial` (🟡, `proposal` draft→envio gated), `propor_kit` (🔵, `kit_orchestrator`).
4. **Onda B:** `propor_substituicao` (propor→humano) + tabela `op_substituicao_propostas` (migration) — operacional read-only preservado.
5. **Onda C** (🔴, reusa gates provados): `propor_lote_pagamento` → grava proposta que entra no fluxo `folha_lote_service`/`InterPaymentService` (aprovação humana + OTP executa; agente só propõe, ≤ teto); `propor_esocial` → marca evento pendente que o humano transmite via `esocial_tasks` (nunca o agente transmite).
6. **Wiring:** as tools de ação entram no registry escopado (peça 3) — aparecem SÓ pra quem tem o módulo+role; a proposta cai no sino do aprovador por RBAC.
7. **Fila de aprovação:** reusa a entrega/sino da 5.3; a aprovação humana é nas telas/fluxos existentes (não criar novo executor).

## Testabilidade / oráculos (as INVIOLÁVEIS provadas)
- **LLM nunca executa:** cada tool de ação só cria pendente; grep + teste provam ZERO chamada de execução no handler; a tabela-alvo ganha 1 pendente, o estado de execução (pago/transmitido/enviado) permanece intocado.
- **Dinheiro-que-sai sem OTP → impossível:** propor_lote cria pendente; a execução exige o OTP humano existente (prova: pendente criado, nenhum pagamento executado sem OTP).
- **RBAC:** tool de ação de um domínio não aparece/recusa pra quem não tem o módulo+role; aprovador errado não aprova.
- **3 papéis:** o ator que propôs não consegue aprovar a própria proposta (inforjável).
- **Idempotência:** 2 propostas idênticas → 1 pendente.
- **eSocial:** proposta não transmite; só marca pendente pro humano.
- Verificar pela rota real com identidade de cada tier (bancada throwaway, nunca :8080/green); limpeza por id, 0 remanescentes, nunca apaga real. Mutação-teste do gate.
