# Fase 5.3 — Proativo por evento: regras de gatilho + cérebro redator + sino real (Design/Spec)
**Data:** 2026-07-24 · Antecede: 5.2a (Hermes+orquestrador, deployado) e Peça 3 (chat escopado por perfil, deployada; sino real RdBell no ar). Discovery: `.superpowers/sdd/discovery-5.3-proativo.md`.

## Objetivo (uma frase)
O ERP passa a AVISAR sozinho: regras determinísticas detectam condições que importam (posto descoberto, certidão vencendo, caixa baixo, aging, justificativa parada…), o cérebro **redige** o alerta (nunca decide), e a entrega cai no **sino real** respeitando a matriz RBAC — com dedup e anti-spam (digest diário).

## Decisões do dono (2026-07-24, vinculantes)
- **TODAS as famílias ligadas** ("TODOS, ABSOLUTAMENTE TODOS"): postos descobertos · certidões/documentos vencendo · caixa baixo por CNPJ · aging/inadimplência (reforço do existente) · justificativas de ponto paradas · jurídico (prazos/processos) · recrutamento — as duas últimas implementadas desde já, honestamente silenciosas até existir dado (juridico_prazos=0 e candidates sem funil hoje; acordam sozinhas).
- **Limiar caixa baixo:** saldo do CNPJ `< 1 folha mensal do PRÓPRIO CNPJ` (dinâmico; folha por CNPJ via colaborador ativo — caixa_service). Fallback honesto: CNPJ sem folha própria (Eletrônica hoje) → limiar alternativo R$10.000 fixo (não alertar em cima de folha inexistente).
- **Destinatários = matriz RBAC:** postos descobertos + justificativas paradas → diretoria + gestores (roles admin, gerente_operacional, supervisor); certidões → diretoria; caixa + aging → SÓ diretoria (admin) — LGPD, financeiro nunca chega a gestor. Jurídico → diretoria. Recrutamento → diretoria + gestores.
- **Anti-spam:** alerta individual 1x AO SURGIR a condição (transição não-existia→existe, por correlation_id) + **digest diário 07:00 Manaus** consolidando TUDO que persiste (1 notificação única "Bom dia — o que precisa da sua atenção"). Condição resolvida sai sozinha do digest.

## Arquitetura (3 frases — da discovery, mínima sem retalho)
Um avaliador periódico em **celery-beat** (padrão vivo do projeto; NÃO event-handlers com LLM, NÃO APScheduler) roda as **regras SQL determinísticas** (cada uma re-deriva da FONTE — idempotente) e compara com o estado anterior (dedup por `correlation_id`, padrão do `alert_ingest.enqueue_alert`). Condição NOVA → o **cérebro redige** o texto do alerta via `consultor_hub.gerar` (LLM SÓ redige; a decisão de disparar é 100% da regra SQL; LLM caiu → template determinístico com os números). Entrega: role-scoped via `communication_alerts` (target_roles) e/ou inbox `communication_notifications` por user — os DOIS já lidos pelo RdBell; push FCM best-effort; digest 07h consolida persistentes.

## Tech stack
celery-beat (`backend/celery_app.py`, filas isoladas, retry/backoff) · regras SQL cru (`text()`, read-only) · `consultor_hub.gerar` (redator; groundedness nos números do template) · `alert_ingest.enqueue_alert`/`NotificationService`/`notification_triggers._enviar_alerta` (entrega+dedup existentes) · `communication_alerts.target_roles` (RBAC) · TZ Manaus canônico p/ datas.

## Global Constraints (inegociáveis, herdadas)
- **LLM NUNCA decide disparo** — só redige o texto de uma condição já detectada por SQL. Degrada p/ template. Nenhuma ação automática: alerta INFORMA; agir continua humano (e dinheiro-que-sai continua OTP).
- **Financeiro (caixa/aging) só chega a role admin** (diretoria). Matriz RBAC governa TODO destinatário.
- **Nunca fabricar:** regra sem dado → silêncio honesto (não "0 alertas fake"); número no alerta = o da query (groundedness no redator).
- Dedup por `correlation_id` determinístico (ex.: `posto_descoberto:{post_id}`, `certidao:{id}:{expiry}`, `caixa_baixo:{cnpj_slug}:{ano-mes}`); re-alerta individual SÓ em transição; persistência vai pro digest.
- Regras read-only no banco; task roda FORA do worker web (celery); falha de uma regra não derruba as outras (isolamento por try/except + log).
- Deploy: blue-green baked; testes em bancada throwaway (nunca green/:8080); teste que escreve limpa no finally (0 remanescentes); sem pytest (standalone); git add só dos próprios arquivos; commits --no-verify + Co-Authored-By Opus 4.8.

## Componentes
1. **`proativo/regras.py`** — registry de regras declarativas: cada regra = {nome, família, query-detecção (SQL), correlation_id_fn, destinatários (roles), severidade, template_fallback}. Fail-closed: regra sem destinatário/rol não registra. As 7 famílias:
   - `posto_descoberto` (posts.current<required, ativo) → admin+gerente_operacional+supervisor
   - `certidao_vencendo` (ged_certidoes.expiry_date ≤ +30d ou vencida) → admin
   - `caixa_baixo_cnpj` (caixa_por_cnpj: saldo < folha do CNPJ; fallback R$10k) → admin
   - `aging_reforcado` (receivable_accounts vencidas: total+valor; consolida com o reconciliador existente, não duplica) → admin
   - `justificativa_parada` (gp_justifications status='pendente' há >48h) → admin+gerente_operacional
   - `juridico_prazo` (juridico_prazos ≤ +7d; processos escalonar) → admin — silenciosa até ter dado
   - `recrutamento_parado` (candidates sem movimento >7d quando houver funil) → admin+gerente_operacional — silenciosa
2. **`proativo/avaliador.py`** — task celery `proativo.avaliar_regras` (beat */15min): roda regras, diffa contra estado (correlation_ids já alertados ativos), dispara só transições; grava estado (tabela pequena `proativo_alert_state` ou reusa notification_queue/correlation do alert_ingest — decidir no plano pelo que exigir MENOS peça nova).
3. **`proativo/redator.py`** — recebe {regra, dados} → chama `consultor_hub.gerar` com prompt curto ("redija alerta de 2 frases, números EXATOS fornecidos, tom direto") → groundedness nos números → fallback template. NUNCA tool-calling aqui (é só redação).
4. **`proativo/digest.py`** — task beat 07:00 Manaus: consolida condições PERSISTENTES por destinatário (respeitando RBAC por role) numa única notificação "resumo da manhã"; redator idem.
5. **Entrega** — reusa `_enviar_alerta`/NotificationService (inbox por user, resolvendo users por role) e/ou `communication_alerts` target_roles; push FCM best-effort. AMBOS já aparecem no RdBell (nada de frontend novo).

## Testabilidade / oráculos
- Cada regra: teste standalone que PROVA (a) detecção contra o dado real de hoje (postos=2, certidões=3, caixa Inter+Cora disparam, aging=21, justificativa=1; juridico/recrutamento=0 silencioso); (b) dedup — rodar 2x não duplica (transição only); (c) destinatário: alerta financeiro NUNCA gera notificação para user não-admin (query no banco pós-teste); (d) limpeza: toda notificação de teste deletada por id, 0 remanescentes.
- Redator: número do alerta == número da query (groundedness); LLM off → template com números corretos.
- Digest: 2 condições persistentes → 1 notificação única por destinatário.
- E2E: task rodada na bancada → notificação REAL visível via GET /notificacoes com token do destinatário (e ausente p/ quem não deve ver) → deletada no finally.
