# Fase 5.4b — Skills/playbooks por agente + enriquecimento de personas (Design/Spec)
**Data:** 2026-07-25 · Antecede: 5.4 (propor→aprovar, deployada). Discovery: subagente a5daca2 (2026-07-25).

## Objetivo (uma frase)
Tornar os agentes mais assertivos com **conhecimento de domínio real** (CCT/regime/ISS Manaus/prazos) e **playbooks** (procedimentos recorrentes), reusando o padrão JÁ PROVADO do Jurídico — sem burlar nenhuma parede e sem inventar DSL nova.

## Achados da discovery que governam o design
- **O `agent_knowledge/*.md` (embeddings RAG) só serve o bot WhatsApp** (`agent_service.py`), NÃO os 8 consultores/orquestrador. "Reusar agent_knowledge" da spec 5.4 = na prática, generalizar o padrão do Jurídico (que É o RAG-que-ensina-sem-rebuild dos consultores).
- **O Jurídico já tem o modelo certo:** `juridico/conhecimento_service.py` — 2 tabelas (`juridico_conhecimento` precedentes, `juridico_playbook` procedimentos: situacao/area/gatilho/passos JSONB/base_legal/documentos), RAG-lite (área+overlap de keywords, sem embeddings), `contexto_para_prompt(db,area,texto)` injeta no system_prompt. Editável por INSERT, sem rebuild.
- **Personas = strings Python**, 1 arquivo por consultor (cfo_service.py `_REGRAS_COMUNS`/`_PROMPTS_AREA`/`_contexto_empresa`, etc.). CFO já hardcoda CCT/ISS/regime — é o ponto de plugue.
- **Os 8 consultores C-level NÃO têm tool de escrita** (usam `consultor_hub.gerar` puro, sem tool_calls) → playbook neles só NARRA (não executa, não burla RBAC). Ações gated (propor→aprovar) vivem SÓ no orquestrador escopado + Onda A/B/C.
- **Risco de burla (a vigiar):** nada estrutural impede um handler novo de chamar um serviço direto pulando `propor()` — só convenção/review. Não há teste que trave isso.

## Decisão de arquitetura (substrato ÚNICO, sem retalho)
**Generalizar o padrão do Jurídico para um serviço compartilhado `consultor_conhecimento`**, com substrato **file-based** (`uploads/agent_knowledge/consultores/<agente>.md`, montado como volume — ensina sem rebuild, editável pelo Jordan direto no arquivo), lido em runtime e injetado no system_prompt de cada agente. Escolha file-based (não nova tabela DB) porque: (a) a spec 5.4 pede "reusar agent_knowledge/*.md"; (b) Jordan edita markdown, não INSERT; (c) menos código/migração (YAGNI, economia de token). O Jurídico fica como está (já funciona; não migrar).

**Camadas de assertividade** (a 3ª camada da spec): grounding (feito 5.2a) → **persona/domínio (esta fase)** → **playbooks (esta fase)**.

## Componentes
1. **`consultor_conhecimento_service.py`** (novo, em modules/ai/conversation/services/) — `carregar(agente)` lê `uploads/agent_knowledge/consultores/<agente>.md` (cache por mtime, releitura runtime = sem rebuild); `contexto_para_prompt(agente, texto_pergunta, *, max_secoes=3)` retorna as seções `## ` mais relevantes por overlap de keywords (RAG-lite, molde Jurídico — SEM embeddings, YAGNI). Fail-open: arquivo ausente → string vazia (nunca quebra o chat), NUNCA fabrica.
2. **Conteúdo (o valor real, editável)** — 1 `.md` por agente com 2 blocos: `# Conhecimento` (fatos de domínio REAIS: CCT SINDECOMPRESTS AM000613/2025, piso 2026 R$1.670, regime por CNPJ [Eletrônica lucro real→Simples, Patrimonial Simples], ISS Manaus, prazos fiscais/eSocial, liminares PIS/COFINS/INSS) e `# Playbooks` (procedimentos: situação → passos → o que verificar). Agentes: cfo, fiscal, juridico(complementa DB), operacional/coo, comercial/cmo, chro/dp, ged, ceo. Fonte = Jordan/dado do repo; nunca inventar número.
3. **Injeção nas personas** — cada `consultor_*_service.py` e o `consultor_escopado_controller._SYSTEM_BASE` + `portal_cliente._SYSTEM_CLIENTE` ganham 1 linha: concatenam `consultor_conhecimento_service.contexto_para_prompt(<agente>, pergunta)` ao system_prompt (ponto exato: onde já concatenam `_contexto_empresa`/`contexto_compartilhado`). Mudança mínima e aditiva.
4. **Playbooks executáveis (orquestrador escopado)** — NÃO são código novo (evita o risco de burla). São **receitas em texto** no `.md` que orientam o LLM a encadear as tools JÁ registradas (o engine já é multi-step, max_rounds=6), terminando em `propor()` quando é ação. Ex.: "cobrir posto" → o playbook descreve: consultar posto descoberto (tool leitura) → identificar candidato (tool) → `propor_substituicao` (gated). Zero nova porta de execução.
5. **Hermes (diretoria)** — playbooks entram como seção nova `## Playbooks` no `hermes-runtime/SOUL.md` (texto; Hermes já orquestra as tools MCP). Sem mecanismo novo.
6. **Guarda anti-burla (fecha o risco da discovery)** — teste standalone que varre `acoes/*.py` + handlers de tool e falha se um handler de ação de dinheiro/legal chamar serviço de execução direto sem passar por `propor()` (grep AST: nenhum `import`/call de pagar/executar/transmitir fora da primitiva). Vira parte da suite de oráculos.

## Global Constraints (invioláveis, herdadas)
- Conhecimento/playbook = TEXTO que orienta; NUNCA cria caminho de execução novo. Ação continua só via tools gated (`propor()`), RBAC server-side, dinheiro/legal humano+OTP.
- Nunca fabricar: conhecimento = fatos reais (Jordan/repo); groundedness segue valendo na resposta.
- Read-only preservado (operacional/jurídico narram/propõem, não alteram).
- Ensina sem rebuild (arquivo relido em runtime). Fail-open (sem .md → não quebra).
- Deploy: docker cp dos .md pro volume (ou já montado) — sem rebuild p/ conteúdo; serviço novo = blue-green. Bancada throwaway; git add só dos próprios; commits --no-verify + Co-Authored-By Opus 4.8; TZ Manaus.

## Testabilidade / oráculos
- `contexto_para_prompt` retorna seções certas por keyword; arquivo ausente → vazio (fail-open), nunca exceção.
- Injeção: o system_prompt de cada agente passa a conter o bloco de domínio quando o .md existe (teste por-agente).
- Anti-burla: mutação — introduzir um handler que chama serviço de execução direto → o guard FALHA (morde).
- Nunca fabricar: o serviço só devolve o que está no .md (sem completar lacuna).
- E2E leve: pergunta de domínio a um consultor (ex.: CFO sobre piso CCT) → resposta cita o fato real do .md; groundedness passa.

## Fora de escopo (nomeado)
- Embeddings RAG p/ consultores (YAGNI — keyword-match basta; migrar p/ embeddings só se o corpo crescer).
- Migrar Jurídico DB→arquivo (já funciona).
- 5.4c (José Luís cliente-facing) e 5.5 (memória que aprende) — fases próprias.

## Resumo de 1 linha
Generaliza o padrão provado do Jurídico num serviço `consultor_conhecimento` file-based (ensina sem rebuild) + playbooks-como-receita-de-texto sobre as tools gated existentes + guarda anti-burla — agentes mais assertivos, zero parede nova furada.
